Persistence — startup & scheduled tasks

        
Matching alerts: An executable or script was added to the startup folder · An uncommon file added to startup-related Registry keys · Uncommon local scheduled task creation via schtasks.exe

        
Critical

        
Progress: 0 / 5 steps complete

      

      

        

          

            
✓

            
01

            

              
Confirm the affected host is online and has an agent

              
Verify the endpoint has an active XDR agent before investing time in deeper queries.

              
Look for: endpoint_status = Online, recent last_seen timestamp. If agent is missing or stale, raise with client before proceeding.

              
            

          

        

        

          

            
✓

            
02

            

              
Check for scheduled task creation events

              
Query for Windows event 4698 — scheduled task created. Run fleet-wide first to see if this is isolated or widespread.

              
Look for: Unexpected task names, tasks pointing to temp/appdata paths, tasks created by non-admin users or unusual accounts.

              
            

          

        

        

          

            
✓

            
03

            

              
Check for files written to startup or suspicious locations

              
Look for files dropped into temp, appdata, or startup folders around the time of the alert.

              
Look for: Executables or scripts (.exe, .ps1, .bat, .vbs) written to startup paths. Note the process that wrote them — that's your likely initial access vector.

              
            

          

        

        

          

            
✓

            
04

            

              
Check what the dropped file spawned

              
If a suspicious file was found, check whether it was executed and what child processes it created.

              
Look for: cmd.exe, powershell.exe, or network-connected processes spawned from the suspicious parent. Any results here = likely True Positive, escalate.

              
              
            

          

        

        

          

            
✓

            
05

            

              
Check login context around the alert time

              
Establish who was logged into the host when the persistence mechanism was created.

              
Look for: Unexpected usernames, logins from unusual source IPs or workstations, or service account interactive logins. Cross-reference with the alert timestamp.

Lateral movement / RDP anomaly

        
Matching alerts: Rare RDP session to a remote host · Suspicious SMB connection from domain controller

        
High

        
Progress: 0 / 5 steps complete

      

      

        

          

            
✓

            
01

            

              
Confirm source host agent status

              
Verify the host initiating the RDP/SMB connection has an active agent and is a known asset.

              
Look for: Is this a server, workstation, or service host? A WSUS server, print server, or DC initiating RDP to workstations is immediately suspicious.

              
            

          

        

        

          

            
✓

            
02

            

              
Pull all RDP connections from the source host

              
Get the full picture of RDP activity originating from this host — not just the single connection that triggered the alert.

              
Look for: Multiple destination IPs, connections outside business hours, or RDP from a process with no legitimate reason to initiate remote desktop sessions.

              
            

          

        

        

          

            
✓

            
03

            

              
Count unique RDP destinations from the source

              
Aggregate RDP destinations to assess spread — a single host RDP'ing to many others is a strong lateral movement indicator.

              
Look for: High connection_count to multiple unique IPs. 3+ unique destinations from a non-admin host = escalate immediately.

              
            

          

        

        

          

            
✓

            
04

            

              
Check who was logged into the source host

              
Establish what user account was active on the source host around the time of the RDP activity.

              
Look for: Service accounts logging in interactively, accounts that don't belong on that host, or logins from unusual source IPs preceding the RDP activity.

              
            

          

        

        

          

            
✓

            
05

            

              
Check firewall for corroborating traffic

              
Confirm the RDP traffic was seen at the network layer and whether it was allowed or blocked.

              
Look for: session_end_reason — if "aged-out" or "policy-allow" the connection succeeded. If "policy-deny" it was blocked. No firewall record at all = possible internal VLAN hop not traversing the firewall.

Malware / local analysis / file threat

        
Matching alerts: Local Analysis Malware · An uncommon executable was remotely written over SMB · Wildfire malicious verdict

        
Critical

        
Progress: 0 / 6 steps complete

      

      

        

          

            
✓

            
01

            

              
Get Wildfire verdict on the file hash

              
Confirm the sandbox verdict for the file hash associated with the alert.

              
Look for: action_file_wildfire_verdict — malicious/grayware = investigate further. Benign = likely FP but still check for unusual delivery context. No verdict = file hasn't been submitted to Wildfire yet.

              
            

          

        

        

          

            
✓

            
02

            

              
Check the firewall threat log for the file

              
See if the file was caught at the perimeter by the NGFW threat engine.

              
Look for: verdict field — malicious confirms the file. sub_type and threat_name_firewall give context on the threat category. source_user tells you who downloaded it.

              
            

          

        

        

          

            
✓

            
03

            

              
Check how many hosts have seen this file

              
Scope the potential spread — how many endpoints have a file event for this filename.

              
Look for: Multiple hostnames = widespread delivery, possibly a phishing campaign or network share infection. Single host = contained, but still needs full investigation.

              
            

          

        

        

          

            
✓

            
04

            

              
Check if the file was directly executed

              
Determine whether the file has been launched as a process — this changes severity significantly.

              
Look for: Any results = file was executed, escalate. No results = file present but not yet run. Note: absence of results does not rule out indirect execution (e.g. DLL sideloading).

              
            

          

        

        

          

            
✓

            
05

            

              
Check what the file spawned

              
If the file was executed, look at what child processes it created.

              
Look for: cmd.exe, powershell.exe, wscript.exe, or any network-connected child processes. Shell spawning = code execution confirmed, escalate immediately.

              
              
            

          

        

        

          

            
✓

            
06

            

              
Check for outbound connections after execution

              
Look for C2 callbacks or data exfiltration following the execution.

              
Look for: Connections to rare/external IPs, uncommon TLDs, or high-frequency beaconing patterns. Cross-reference destination IPs with VirusTotal.

Suspicious process / LOLBIN / PowerShell

        
Matching alerts: Suspicious PowerShell Command Line · LOLBIN process executed with a high integrity level · Notepad process makes a network connection · Execution of an uncommon process at an early startup stage

        
High

        
Progress: 0 / 5 steps complete

      

      

        

          

            
✓

            
01

            

              
Review PowerShell script block content

              
If the alert involves PowerShell, pull the actual script content from event 4104 logging.

              
Look for: Base64 encoded strings, IEX (Invoke-Expression), DownloadString, WebClient, or references to known C2 frameworks (Cobalt Strike, Metasploit, Empire). Encoded content = almost always malicious.

              
            

          

        

        

          

            
✓

            
02

            

              
Check what spawned the suspicious process

              
Identify the parent process — this tells you the initial access vector.

              
Look for: Office apps (winword, excel), PDF readers, browsers spawning PowerShell or cmd = likely phishing/malicious document. explorer.exe or unusual parents are also worth escalating.

              
              
            

          

        

        

          

            
✓

            
03

            

              
Check for files dropped to disk

              
Determine whether the process wrote any files to suspicious locations.

              
Look for: Executables, scripts, or DLLs written to temp/appdata/startup. A process dropping files = likely second-stage payload delivery.

              
            

          

        

        

          

            
✓

            
04

            

              
Check for outbound network connections from the process

              
Look for the suspicious process making external connections — callback, C2, or data exfil.

              
Look for: Connections to external IPs from notepad.exe, powershell.exe, or other LOLBINs that have no legitimate reason to make network connections. Any result here is a strong True Positive indicator.

              
            

          

        

        

          

            
✓

            
05

            

              
Check if the same process is running fleet-wide

              
Determine whether this is isolated to one host or part of a broader campaign.

              
Look for: Same suspicious process name appearing on multiple hosts. Fleet-wide spread = likely automated malware campaign, escalate immediately with full host list.

C2 / DNS / beaconing

        
Matching alerts: Abnormal Recurring Communications to a Rare Domain With a Less Common Port · Suspicious DNS Query (generic:...) · generic: alerts

        
Critical

        
Progress: 0 / 5 steps complete

      

      

        

          

            
✓

            
01

            

              
Confirm DNS queries to the suspicious domain

              
Verify the domain in the alert is being queried via the DNS query name field — more precise than hostname matching.

              
Look for: Repeated queries to the same domain, queries from multiple hosts (potential fleet-wide C2), or queries at regular intervals (beaconing pattern). Check the domain on VirusTotal.

              
              
            

          

        

        

          

            
✓

            
02

            

              
Check for connections to suspicious TLDs

              
Broaden the search — check if the host is connecting to any other uncommon TLDs beyond the one in the alert.

              
Look for: .xyz, .top, .ru, .cn, .tk, .onion domains. Multiple suspicious TLD connections from one host = strong C2 indicator. Note all domains for VirusTotal checks.

              
            

          

        

        

          

            
✓

            
03

            

              
Fleet sweep — any other hosts connecting to the IOC IP

              
Check whether any other hosts on the estate are communicating with the same C2 IP.

              
Look for: Multiple hosts connecting to the same external IP = widespread campaign. Note all affected hostnames for the incident report. Single host = contained but still investigate.

              
            

          

        

        

          

            
✓

            
04

            

              
Identify the process making the connections

              
Determine what process on the endpoint is responsible for the C2 communication.

              
Look for: Unexpected processes making external connections (notepad.exe, svchost.exe from wrong path, renamed system binaries). Check actor_process_image_path — legitimate svchost runs from System32 only.

              
              
            

          

        

        

          

            
✓

            
05

            

              
Check firewall — was the connection allowed or blocked?

              
Confirm at the network layer whether the C2 traffic reached its destination.

              
Look for: action = allow and session_end_reason = aged-out = active C2 session, escalate immediately. action = deny = blocked but host is still infected, needs remediation. No record = traffic may be internal or on a non-monitored interface.
